## 2. 상세 점검 결과

### 영역 A. SQL 인젝션 (SQL Injection)

#### 1) 클라이언트 쿼리 레벨
- **점검 결과**: **안전 (취약점 없음)**
- **분석**:
  - 클라이언트 소스 내에 직접 `SELECT * FROM ... WHERE ...` 같은 Raw SQL 문자열 조립 코드가 전혀 존재하지 않습니다.
  - 연동된 Supabase SDK(`supabase.from('table').select().eq(...)`)는 PostgREST API를 경유하며, 모든 파라미터가 PostgreSQL Prepared Statement 형태로 바인딩되므로 외부 입력값에 의한 SQL 인젝션이 불가능합니다.

#### 2) 서버 DB Function (RPC) 레벨 (향후 작성 시 주의점)
- **점검 결과**: **잠재 위험 (개발 가이드 준수 필요)**
- **분석**:
  - 향후 Supabase SQL Editor에서 사용자 정의 함수(PL/pgSQL)를 작성할 때, `EXECUTE format('SELECT * FROM ... WHERE id = %s', user_input)`과 같이 동적 SQL 문자열을 연결하면 SQLi가 발생할 수 있습니다.
- **방어 대책**:
  - 정적 쿼리 사용을 기본으로 하고, 동적 SQL이 불가피할 경우 반드시 `$1, $2` 플레이스홀더와 `USING` 절을 사용합니다:
    ```sql
    -- [안전한 예시]
    EXECUTE 'SELECT * FROM users WHERE user_id = $1' USING p_user_id;
    ```

### 영역 B. 트래픽 및 클라이언트 데이터 위변조

#### 1) 클라이언트 사이드 재화 조작 취약점
- **위험도**: **HIGH**
- **취약점 분석**:
  - `gameState.darkMatter` (DM)
  - `progress.stages` (스테이지 클리어 및 별 달성)
  - `progress.levels` (파츠 강화 레벨)
  - `progressGrowth.cores`, `shards` (스킬 코어 및 파츠 조각)
  - 위 값들이 브라우저 메모리와 `localStorage['mo_v2_save']`에서 관리되고 있습니다.
  - **공격 시나리오**: 브라우저 콘솔(`F12`)에서 `gameState.darkMatter = 99999999; progress.save();` 명령을 실행하거나, Supabase로 전송되는 REST API 패킷을 Fiddler/Burp Suite로 가로채 `{ dm: 99999999 }`로 변조하여 전송할 수 있습니다. RLS가 "본인 행 수정 허용"으로 되어 있더라도 값 자체의 무결성은 검증하지 못합니다.

#### 2) 스테이지 클리어 시간 및 보상 위변조
- **위험도**: **HIGH**
- **취약점 분석**:
  - `battle_v2.js`의 `finishBattle()`에서 클리어 시간(`this.stats.time`)을 클라이언트 타이머로만 기록합니다.
  - 보스 스테이지를 0.1초 만에 클리어했다고 패킷을 위조하여 3성을 달성하고 보상을 획득하는 치팅이 가능합니다.

#### 3) 트래픽 위변조 방어 대책
1. **서버 검증형 보상 RPC 도입 (필수 권장)**:
   - 클라이언트는 스테이지 결과 보고서(`{ stage_id: '1-1', clear_time: 45.2, kill_count: 12 }`)만 전송합니다.
   - Supabase DB Function에서 **이전 스테이지 해금 여부**, **최소 클리어 가능 시간(예: 1-1은 최소 15초 이상)**을 검증하고, 검증 통과 시 서버 DB에 정의된 `stage_rewards` 표에 따라 서버가 직접 DM과 별을 지급합니다.
2. **DB 스키마 CHECK 제약 조건 적용**:
   - DB 테이블 생성 시 터무니없는 수치가 입력되는 것을 스키마 레벨에서 원천 차단:
     ```sql
     ALTER TABLE user_progress ADD CONSTRAINT chk_dm_range CHECK (dark_matter >= 0 AND dark_matter <= 50000000);
     ALTER TABLE user_parts ADD CONSTRAINT chk_part_level CHECK (level >= 1 AND level <= 10);
     ```
3. **Row Level Security (RLS) 정책**:
   - 재화 테이블은 클라이언트의 직접 `UPDATE`를 금지하고, 서버 RPC 함수(`SECURITY DEFINER`)를 통해서만 잔고가 변경되도록 권한을 통제합니다.

### 영역 D. 일반 웹 취약점 (XSS, CSRF, LocalStorage)

#### 1) Cross-Site Scripting (XSS)
- **점검 결과**: **안전**
- **분석**:
  - 코드베이스 전체에서 `innerHTML` 사용처가 67군데 존재하지만, 모두 고정된 내부 게임 데이터(파츠 이름, 수치, 스킬 설명 등)를 렌더링하고 있습니다.
  - 외부 사용자로부터 문자열을 입력받는 `<input type="text">`, 닉네임 입력, 채팅창이 현재 존재하지 않으므로 XSS 벡터가 없습니다.
  - *향후 닉네임 입력 기능 추가 시 `textContent` 사용 또는 `DOMPurify` 적용 필요.*

#### 2) LocalStorage 조작
- **점검 결과**: **단일 기기 내 변조 가능 (온라인 동기화 시 정합성 검증 필요)**
- **대응책**:
  - 클라우드 동기화 도입 시, 로컬의 변조된 데이터가 서버의 정상 데이터를 덮어쓰지 못하도록 **서버 저장 타임스탬프 및 버전(Revision) 비교 로직**을 적용해야 합니다.

## 4. 데이터베이스 및 RPC 동시성/무결성 정밀 점검 (2026-11-01 2차 점검)

현재 구현된 DDL 및 RPC(`MD/설계_DBDDL.md`)에 대해 동시성(Race Condition), RLS 컬럼 제어, 트랜잭션 무결성 관점에서 2차 정밀 점검을 실시한 결과입니다.
**※ 주의**: 타 기능 브랜치가 `main`에 완벽히 병합된 후, 아래 취약점과 해결책을 반영하여 DB 패치를 적용하도록 로드맵에 보관합니다.

### 1) [P0] `users_update_own` RLS 컬럼 누수 (유료 권한 자가 변조 취약점)
- **현상**: `public.users`의 UPDATE 정책(`auth.uid() = id`)은 특정 컬럼이 아니라 대상 행 전체 수정을 허용함.
- **취약점**: 클라이언트 개발자 콘솔(`F12`)에서 `supabase.from('users').update({ has_no_ads: true, auto_dispatch_until: '2099-12-31' })`를 호출하면 광고제거 및 자동 파견 패스 권한을 유저가 스스로 획득할 수 있음.
- **조치 계획 (병합 후 적용)**:
  - `users` 테이블의 일반 유저 직접 `UPDATE` RLS 정책 완전 회수(`DROP POLICY`).
  - 닉네임 변경은 오직 닉네임만 검증/수정하는 전용 RPC 함수(`set_nickname(p_nickname TEXT)`)로 분리.

### 2) [P0] `settle_battle` / `upgrade_part` 행 잠금(`FOR UPDATE`) 누락 (동시성 재화 복사)
- **현상**: `SELECT stages INTO ...` 및 `SELECT dark_matter INTO ...`에서 `FOR UPDATE` 행 잠금이 누락됨.
- **취약점**: 네트워크 지연 중 클라이언트가 클리어 패킷을 동시 다중 전송하거나 2개 탭에서 동시 정산 시, 두 트랜잭션 모두 "기존 별 0개"를 읽어 각각 3개씩 총 6개의 별과 2배의 다크매터를 복사 지급함 (Race Condition).
- **조치 계획 (병합 후 적용)**:
  - `SELECT stages ... FROM public.user_stage_records ... FOR UPDATE;`
  - `SELECT dark_matter ... FROM public.user_wallets ... FOR UPDATE;`
  - 유저 행에 배타적 락을 걸어 트랜잭션을 엄격히 직렬화(Serialization).

### 3) [P0] 상위 난이도 진행도 누락 시 "무한 보상 복사" 취약점
- **현상**: 가입 시 `user_stage_records`는 `difficulty = 'normal'` 1행만 생성됨. `hard`, `hell` 클리어 시 빈 객체로 계산 후 `UPDATE`를 실행하나 대상 행이 없어 0건 수정되고 정상 종료됨.
- **취약점**: DB에 진행도가 저장되지 않았으므로 다음 정산 요청 시에도 매번 최초 3성 클리어로 판정되어 별과 다크매터를 무한 복사할 수 있음.
- **조치 계획 (병합 후 적용)**:
  - 단순 `UPDATE` 대신 `INSERT INTO public.user_stage_records ... ON CONFLICT (user_id, difficulty) DO UPDATE SET stages = ...` 업서트(Upsert)로 전환.

### 4) [P0] 파츠 강화(`upgrade_part`)의 기존 속성 삭제 및 미보유 파츠 생성 버그
- **현상**: 미보유 파츠 요청 시 에러 없이 레벨 1로 간주하여 2레벨 파츠를 신규 생성함. 또한 갱신 시 `jsonb_build_object('lv', ...)`로 파츠 객체 전체를 덮어씀.
- **취약점**: 미보유 파츠 부정 생성 가능, 기존 파츠에 저장된 `grade`(등급), `opts`(옵션), `skills` 메타데이터가 통째로 삭제되어 인벤토리 데이터 유실 발생.
- **조치 계획 (병합 후 적용)**:
  - 파츠 미보유(`NOT (v_inventory ? p_part_id)`) 시 즉시 `RAISE EXCEPTION`으로 차단.
  - 레벨 갱신 시 `jsonb_set(v_inventory, ARRAY[p_part_id, 'lv'], to_jsonb(v_part_level + 1))` 형태로 `lv` 필드만 부분 갱신.

### 5) [P1] 업적 `jsonb_set` 중첩 부모 객체 부재 오류
- **현상**: PostgreSQL의 `jsonb_set`은 빈 객체 `{}`에서 `{total_kills, cur}`처럼 부모 키가 없으면 하위 키를 생성하지 못함.
- **조치 계획 (병합 후 적용)**:
  - 가입 트리거 시 `achievements` 기본 뼈대(`{"total_kills": {"cur": 0, "max": 0}}`)를 생성해 두거나, 부모 객체 안전 초기화 보장.

### 6) [P1] `SECURITY DEFINER` 함수 경로 보안
- **조치 계획 (병합 후 적용)**:
  - 모든 RPC 함수 상단에 `SET search_path = public;`을 명시하여 search_path 하이재킹 차단.

## 5. 서버 & 디비 다층 방어 구축

### 5.1. 서버 및 디비 분리 필요성
1. **DB는 외부 세계와 통신할 수 없음**: 구글/애플 인앱결제(IAP) 영수증 유효성을 검증하려면 외부 결제 서버와 HTTPS 통신을 해야 하지만, DB는 외부 API를 호출하지 못함.
2. **복잡한 게임플레이 휴리스틱 연산 부적합**: 캐릭터 스펙(공격력, 이동속도, 사거리)과 몬스터 스폰 주기, 스테이지 총 체력 등을 기반으로 "이 클리어 타임이 물리적으로 가능한가?"를 판정하는 수식을 SQL로 짜면 DB CPU 부하가 폭증함.
3. **디도스/광클 무차별 요청 방어 불가**: 1초에 수십 회 패킷을 연타하는 클라이언트를 DB 프로시저로 막으려 하면 매번 DB 커넥션을 맺어야 하므로 커넥션 풀 고갈 장애가 발생함. 서버사이드 인메모리(Rate Limit)에서 DB를 건드리지도 못하게 튕겨내야 함.
4. **동적 파츠 옵션 및 드랍 테이블 연동**: 수시로 밸런스 패치되는 파츠 드랍율(`rollBattleDrop`)과 등급 승급 공식을 SQL 프로시저에 복제해두면 클라이언트와 서버 간 데이터 불일치가 필연적으로 발생함.

### 5.3. 3-Tier 아키텍처 연동 흐름
```
[클라이언트 (v2 엔진)]
       │
       ▼ (1. 행동 요청: e.g. "스테이지 1-1 클리어 보고", "파츠 강화 요청")
[서버사이드 레이어 (Supabase Edge Functions / Node.js)]
   • 1차 디바운스 / Rate Limiting (광클 컷)
   • 파라미터 정제 (불법 필드 주입 차단)
   • 비즈니스 연산 (물리 시간 검증, 드랍 추첨, 레벨 공식 계산, JSON 객체 안전 가공)
       │
       ▼ (2. 검증 완료된 확정 명령 전달)
[디비사이드 레이어 (Supabase PostgreSQL)]
   • 행 잠금 (FOR UPDATE - 다기기/동시성 방어)
   • 단일 ACID 트랜잭션 (지갑 증감 + 원장 + 인벤토리 + 진행도)
   • 무결성 하드 제약 (CHECK, FK - 음수 잔고 원천 차단)
```
